# 2026-11-08 개발·디자인 평가와 권장 진행 방향

## 결론과 문서의 지위

현재 easime는 엔진 실험 단계를 넘어, KDE 패키지·설정·트레이와 Windows 한글 입력까지 연결된 초기 제품이다.
공통 코어와 자동 검증 기반은 확장에 적합하다. 다음 투자의 중심은 **기능 수를 늘리기보다 실제 앱에서 글자를 잃지 않고, 상태를 이해하고, 원래 입력기로 돌아갈 수 있음을 확인하는 것**이어야 한다.
디자인도 새 화면을 많이 만드는 것보다 현재의 작은 화면들이 같은 상태를 정확하게 설명하도록 다듬는 편이 프로젝트 목적에 맞다.

이 문서는 기준 시점의 평가와 **권장안**이다. 제품 범위·기본값·릴리스 조건을 새로 확정하지 않는다.
기존 결정은 [decisions.md](decisions.md), 지속적인 디자인 원칙은 [DESIGN.md](../DESIGN.md), 구현 현황은 [status.md](status.md)가 담당한다.
후속 작업은 이 평가를 그대로 구현 승인으로 간주하지 말고 해당 시점의 코드와 사용자 결정을 다시 확인한다.

## 개발자 관점

### 유지할 구조

[ime-session](../crates/ime-session/src/lib.rs)이 엔진 구성, 언어 전환, 설정 반영과 조합 보존을 맡고 프런트엔드는 OS의 키·텍스트 API를 연결한다.
이 분리는 Windows에서도 같은 동작 규칙을 재사용하게 한다. 새 플랫폼마다 한글 조합과 전환 규칙을 복사하지 않는 방향을 유지한다.
OS별 경로와 언어 규칙을 인자로 받아 여러 OS에서 시험하는 방식도 유효하다. 구체적 경계는 [platforms.md](platforms.md)를 따른다.

[InputEngine 계약 검사](../crates/ime-core/src/contract.rs), 가짜 KWin, 실제 Windows TSF와 모의 텍스트 저장소, MSI 설치·제거·업그레이드, Fedora 설정 컨트롤, Debian/Fedora 패키지 검사가 서로 다른 실패 지점을 다룬다.
이 계층은 강점이다. 테스트 개수를 늘리는 것보다 실제 실패 사례를 해당 경계의 회귀 검사로 돌려놓는 편이 낫다.

설정의 알 수 없는 키와 주석 보존, 읽기 실패 시 덮어쓰기 방지, 초기화 백업, KDE 활성화 되돌리기의 현재 값 확인은 복구 가능한 제품의 기반이다.
입력 경로에서 트레이 D-Bus 처리를 분리한 것도 타이핑을 외부 서비스 응답에 묶지 않는 적절한 선택이다.

### 가장 큰 위험은 OS·앱 경계의 검증 부족

엔진 테스트 성공만으로 사용자가 입력한 글자가 실제 문서에 정확히 남는다고 결론낼 수 없다.
조합 중 포커스 이동, 확정과 동시에 앱에 넘기는 Space/Enter, 앱의 조합 종료, 설정 재적용이 주요 확인 지점이다.
Windows의 `OnTestKeyDown`과 `OnKeyDown` 처리 차이, 오른쪽 Alt 탭의 앱 메뉴 영향은 [현재 알려진 한계](platforms.md)에 이미 설명되어 있다.
이를 추측으로 재설계하기보다 대표 앱에서 재현하고 결과를 계약 검사와 어댑터 검사에 나누어 반영해야 한다.

Windows에는 모드 표시·조합 밑줄·후보창이 없고, 앱 사이 모드 공유도 없다.
언어별 TSF 프로필은 사용자 결정이므로 유지한다. 반면 전체 창 공통 입력 상태는 아직 구현되지 않은 약속이다.
두 항목을 같은 것으로 취급하거나 현재의 앱별 상태를 새 기본 정책으로 굳히지 않는다.

### 확장보다 완결할 작업

KDE의 한국어 한자와 일본어 단어 변환은 이미 연결되었다. 우선 최신 패키지에서 사전 포함, 후보 선택·취소, 원문 복귀, 앱 전환을 끝까지 확인한다.
일본어 문절·문맥 변환이나 학습은 현재 단어 변환과 다른 제품 단계다. 기능 이름만으로 이를 지원한다고 표현하지 않는다.

Mac에서는 포터블 코어 개발·검증이 가능하지만 macOS 입력기로 사용할 프런트엔드·FFI·설치 경로는 아직 계획이다.
KDE 코드의 정적 검사나 컨테이너 검증도 실제 KWin 세션을 대체하지 않는다. Mac 개발 환경과 Fedora/Windows 실사용 검증 환경의 역할을 구분한다.
macOS 구현에 착수할 때는 기존 코어를 사용해 키 수신→조합→확정→취소의 작은 경로부터 검증하는 편이 적절하며, 지금 착수한다는 결정은 아니다.

중국어·GNOME·macOS와 클립보드·이모지는 프로젝트 목적에 포함되지만, 현재 입력·복구 경로의 검증을 분산시키지 않도록 후속 단계로 두는 것을 권장한다.
이미 진행된 Windows 작업은 없던 것으로 돌리지 않고, 한국어 입력의 실사용 확인과 최소 상태 표현에 집중하는 것이 좋다.
대규모 공통 UI 추상화나 전면 리팩터링은 현재 증거로 정당화되지 않는다. 성능 역시 측정 전에는 느리다고 단정하지 않는다.

## 동아시아 UX/UI 디자이너 관점

### 유지할 경험

사용자가 전환할 때만 잠깐 표시하고 포커스 진입만으로 표시하지 않는 원칙은 글쓰기 흐름에 맞는다.
트레이에서 상태를 다시 확인할 수 있는 구조, 후보 번호·페이지 이동·Enter·Esc는 키보드 중심 목적에 부합한다.
한자 변환 취소 시 원래 한글을 보존하는 행동은 장식보다 우선하는 디자인 품질이다.

설정 앱은 Kirigami 컨트롤을 사용하고 일반·언어·단축키·한국어·모양으로 나뉜다.
관찰한 일반 화면은 활성화 안내를 상단에, 입력 지원 범위를 그 아래에, 초기화를 별도 구역에 배치한다.
언어 화면은 표시 언어와 입력 언어를 혼동하지 않으며, 지원하지 않는 간체·번체 중국어를 비활성으로 구분한다.
관찰한 네 캡처에서는 주요 문구가 화면 안에 읽히지만, 이것이 모든 번역·창 크기에서 잘린 글자가 없다는 뜻은 아니다.

### 첫 성공을 확인하는 흐름이 부족하다

상단 활성화 버튼과 되돌리기는 중요한 진전이다. 다만 입력기로 선택됨, 데몬 실행 중, 현재 앱에서 입력 성공은 서로 다른 상태다.
[일반 페이지](../settings/kde/qml/GeneralPage.qml)의 상태 문구는 검출한 상태까지만 약속하도록 검토해야 한다.
로그인 이후 실제 입력 확인으로 이어지는 짧은 안내나 시험 과제가 필요하다. 전문가용 설정을 먼저 만든다는 기존 결정을 유지하면서도 가능한 개선이다.
초보자용 대형 마법사를 즉시 추가하는 것을 전제하지 않는다.

한국어 언어 화면 캡처에는 모든 입력 언어가 꺼져 있고 “영어로만 입력합니다”라는 안내가 보인다.
이는 CI의 시스템 언어와 현재 기본값 정책에 따른 정상 상태다. 그러나 다른 언어 시스템에서 설치한 사용자는 입력기 고장으로 오해할 수 있다.
기본값을 임의로 바꾸지 말고, 일반 화면에서 입력 언어 선택으로 이어지는 경로와 현재 선택 결과를 명확히 하는 것을 권장한다.

### 입력 상태와 오류를 사용자가 알 수 있어야 한다

Windows는 영어/한국어 모드를 쳐 봐야 알 수 있다. 한국어 프로필 선택과 그 안의 영어 모드는 다르므로 OS 언어 이름만으로 충분하지 않다.
후보 기능 확장에 앞서 현재 모드와 조합 중인 범위를 알 수 있게 해야 한다. 포커스만으로 박스를 띄우는 동작을 다시 도입하지 않는다.

일본어 사전이 없거나 읽히지 않으면 가나 후보만 나오며 진단은 로그에 있다.
사용자에게 필요한 정보는 내부 파일 구조보다 “현재 가능한 변환”과 “복구할 다음 행동”이다.
설정에서 사전 상태를 확인하고 오류 시 조용한 안내로 접근하게 하되, 키를 칠 때마다 경고창을 띄우지 않는 방향을 권장한다.

### 후보창의 가독성과 네이티브 일체감

[후보 렌더러](../crates/frontend-wayland/src/candidate.rs)는 고정 폭 400, 행 높이 34와 고정 색·글자 크기를 쓴다.
[입력 패널](../crates/frontend-wayland/src/panel.rs)은 scale 1을 사용한다. 시스템 테마·확대 글씨·혼합 배율에 대한 적응이 현재 디자인 약속에 못 미친다.
특히 긴 일본어 후보와 풀이가 폭을 넘는 경우 전체 내용을 확인할 수 있는 방법을 검토해야 한다.
현재 코드는 폭 경계에서 그리기를 제한한다. 실제 사용에서 어느 후보가 읽기 어려운지는 별도 화면 검증이 필요하다.

선택 배경과 `>` 표식을 함께 쓰는 점은 유지한다. 다음 개선은 장식 효과보다 시스템 색·글꼴·배율, 화면 가장자리 배치, 긴 후보의 식별을 우선한다.
직접 그리는 후보창의 의미를 보조 기술에 전달하는 접근성 경로도 검토해야 한다. 픽셀 렌더링과 키보드 선택만으로 스크린 리더 지원을 충족했다고 할 수 없다.

한국어·일본어·중국어를 하나의 “CJK 폰트”로만 평가하지 않는다. 후보 언어에 맞는 지역 글자꼴, 한글 풀이와 한자의 크기 관계, 일본어 가나와 한자의 기준선을 함께 확인한다.
간체·번체 구분은 이미 확정된 입력 언어 정책이다. 둘 다 `中`으로 표시하는 장래 상태 구분은 아직 별도 결정이 필요하다.

### 문구와 설정의 세부 완성도

일본어 모양 화면은 표시 시간을 `1000` 밀리초와 환산 설명으로 보여 준다.
사용자가 조정하려는 것은 체감 시간이다. 초 단위 표현과 실제 표시 미리보기를 권장하되, 기존 저장 형식을 바꿀 필요는 없다.
일반 화면의 경로·로그 정보는 전문가용 목표에 맞으므로 무조건 제거하지 않는다. 입력 준비 상태와 다음 행동보다 앞서지 않도록 정보 순서를 관리한다.

한국어 외 번역은 초안이다. 번체 화면에서 여러 언어의 고유 이름을 보이는 것과, 동작 설명의 자연스러움은 별개로 감수해야 한다.
원어민이 전환·조합·확정·취소·복구를 같은 의미로 이해하는지 확인한다. 한국어 길이에만 맞춘 배치에서 모든 언어가 안전하다고 판단하지 않는다.
전환 키 기본값의 문서상 한/영 키와 코드상 `Both` 불일치는 사용자 결정으로 해소한 뒤 UI·문서·테스트를 함께 맞춘다.

## 권장 작업 순서와 완료 기준

### 1. 최신 KDE 패키지의 실제 입력·복구 검증

- Qt 앱, GTK 앱, 브라우저에서 한국어 조합·삭제·한자 선택과 Esc 복귀, 일본어 단어 후보·페이지 선택, 전환·포커스 이동을 확인한다. 각 앱의 Wayland/XWayland 여부를 기록해 미지원 XIM 경로와 구분한다.
- 트레이 전환 중 조합 보존, 설정 적용, 활성화 확인·되돌리기, 다시 로그인한 뒤 상태를 확인한다. 시스템 변경은 사용자가 확인하고 수행한다.
- 완료 기준: 패키지/커밋, 배포판·KWin·앱 버전, 입력 절차, 기대/실제 문자열, 실패·미시험 항목이 [KDE 기록](kde-testing.md)에 남는다. 태스크바 문제는 KWin 6.8.2에서 해소된 기존 관찰을 보존하고 최신 후보창·상태 표시의 회귀 여부만 추가 확인한다.

### 2. 입력 준비 상태와 후보 읽기 개선

- 1단계에서 관찰한 실패를 먼저 고친다. 사전 상태와 입력 언어 선택 안내, 모드 표현, 긴 후보·배율·시스템 색을 작은 단위로 처리한다.
- 완료 기준: 사전 누락·정상 상태에서 사용자가 가능한 입력과 다음 행동을 알 수 있고, 밝은/어두운 테마·확대 글씨·혼합 배율에서 선택 후보와 풀이를 식별한다. 키보드만으로 설정·복구에 도달하고 접근성 미지원 범위를 명시한다.
- 전환 키 기본값은 결정 전까지 변경하지 않는다. 원어민 감수와 접근성 확인은 코드 테스트와 별도로 기록한다.

### 3. Windows 한국어 경로를 일상 앱에서 확인

- 설치·프로필 선택·한/영 전환·조합·Space/Enter·삭제·포커스 이동·제거를 메모장, 브라우저, 메신저에서 확인한다. 오른쪽 Alt와 앱 메뉴 동작도 포함한다.
- 모드 표시·조합 표시와 앱 사이 모드 공유를 기존 결정에 맞게 설계한다. 후보창 전에는 일본어 프로필을 활성화하지 않는다.
- 완료 기준: 실제 PC 결과와 남은 앱별 한계가 기록되고, 입력 누락·중복 문제는 회귀 테스트로 남는다. CI MSI 생성만으로 일반 배포 준비가 끝났다고 하지 않는다.

### 4. 검증 결과에 따라 확장 범위를 결정

일본어 문절 변환, XWayland, 생산성 팝업, 중국어, GNOME·macOS의 순서는 사용자의 우선순위와 앞 단계의 결과로 정한다.
새 플랫폼의 첫 목표는 많은 설정 화면보다 설치·키 입력·조합·확정·취소·복구의 최소 경로다.
공통 규칙은 코어에, OS 고유 표시는 어댑터에 유지한다. 외부 프로토콜·API 조사는 해당 작업 시 최신 공식 자료로 다시 확인한다.

## v0.1.0을 판단할 때의 권장 기준

출시 범위는 사용자가 정한다. 권장안은 실제 검증한 KDE·언어·앱 범위를 명시한 제한된 첫 릴리스이며, Windows의 실험 상태를 별도로 표시하는 것이다.
모든 예정 플랫폼이나 초보자 UI를 완성해야 한다는 뜻은 아니다.
핵심 판단 근거는 입력 보존, 모드 인지, 후보 취소·복구, 설치와 되돌리기, 알려진 한계의 정확한 안내다.
현재 green CI는 이 판단을 뒷받침하는 자동 검증이며 실제 데스크톱 사용을 대체하지 않는다.
태그와 릴리스는 사용자 결정으로 남긴다. 그전까지 작업은 [AGENTS.md](../AGENTS.md)의 `main` 직접 커밋·즉시 푸시 정책을 따른다.

## 문서 유지 방식

이 문서 변경의 로컬 검증: Mac에서 workspace fmt, 포터블 8개 크레이트의 clippy와 테스트 302개, Linux 타깃 전체 workspace 교차 clippy를 통과했다. AGENTS.md에서 문서·라이선스 24개에 도달하며 로컬 파일 링크가 끊어지지 않음을 확인했다.
Linux 실행 테스트, Qt/Kirigami 설정 실행, Windows TSF 실행은 이 Mac에서 수행하지 않았다. 해당 자동 검증은 위 기준 커밋의 CI 근거와 문서 커밋 후 main CI로 확인하며, 실제 데스크톱 검증과 구분한다.

모든 문서의 입구는 [AGENTS.md](../AGENTS.md)와 [문서 목록](README.md)이다.
새 관찰은 현재 상태 문서에 갱신하고, 확정한 제품 결정만 결정 문서로 옮긴다. 이 날짜의 평가는 당시 근거로 남긴다.
구현, 자동 검증, 실제 환경 확인을 구분하여 기록하고, 하나의 기능이 여러 문서에서 완료/미구현으로 엇갈리지 않게 확인한다.
